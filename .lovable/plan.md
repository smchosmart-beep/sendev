# 평가 제출에 닉네임 비밀번호 소유 검증 추가

## 목표
글·댓글과 동일하게, 평가(`createReview`)도 닉네임 소유를 비밀번호로 검증한다. 이렇게 하면 임의 닉네임 사칭이나 서버 함수 직접 호출을 통한 별점 부풀리기가 차단된다. (새 닉네임을 정식으로 만들어 다시 평가하는 경로는 익명 커뮤니티 방침상 그대로 허용)

## 동작 방식
- 닉네임을 처음 평가에 사용하면 비밀번호가 등록(claim)되고, 이후 같은 닉네임으로 평가할 때는 같은 비밀번호로만 인증된다.
- 이미 글·댓글에서 같은 닉네임을 등록해 둔 사용자는 그때 정한 비밀번호로 그대로 인증된다(닉네임 비밀번호는 글/댓글/평가가 공유).
- "익명"이나 빈 닉네임은 기존처럼 검증을 건너뛴다.

## 변경 사항

### 1. 서버 — `src/lib/platform.functions.ts`
`createReview`를 수정:
- 입력 스키마에 `nicknamePassword: z.string().trim().max(100).default("")` 추가.
- 핸들러에서 upsert 직전에 기존 헬퍼 `ensureNicknameOwnership(db, data.reviewerName, data.nicknamePassword, false)`를 호출. 검증 실패 시 헬퍼가 던지는 에러 메시지(예: "닉네임 비밀번호가 맞지 않습니다.")가 그대로 사용자에게 전달된다.

### 2. 평가 폼 — `src/routes/_main.board.$slug.$postNo.tsx`
`ReviewForm`(별점 제출 컴포넌트) 수정:
- `useStoredIdentity()`(또는 기존 식별자 스토어)를 사용해 저장된 닉네임 비밀번호를 자동으로 채운다. 댓글 폼이 쓰는 것과 동일한 식별자 저장소를 재사용해, 한 번 등록하면 평가에서도 다시 입력하지 않도록 한다.
- 닉네임 입력 아래에 비밀번호 입력 필드 추가: `type="password"`, placeholder "닉네임 비밀번호 (닉네임 입력 시 필수)", 안내 문구("닉네임을 처음 쓰면 비밀번호가 등록되고, 다음부터 같은 비밀번호로 인증합니다").
- `mutation`의 `create({ data: ... })` 호출에 `nicknamePassword` 추가.
- 제출 성공 시 입력한 닉네임/비밀번호를 식별자 저장소에 저장해 다음 평가에서 자동 채움.
- 기기 고정 닉네임(`lockedName`) 흐름은 유지. 비밀번호 필드는 잠금과 무관하게 노출(첫 등록 또는 인증에 필요).

### 3. 가이드 — `src/routes/_main.guide.tsx`
메모리 규칙(기능 변경 시 가이드 동기화)에 따라, 평가 관련 설명에 "평가 시 닉네임 비밀번호로 본인 확인을 한다(닉네임을 처음 쓰면 비밀번호가 등록되고 다음부터 같은 비밀번호로 인증)"는 한 줄을 일반 사용자 눈높이로 추가. 코드/보안 전문 용어는 쓰지 않는다.

## 영향 / 주의
- **행동 변화**: 이제 평가하려면 닉네임 비밀번호가 필요하다. 기존에 평가만 했고 글/댓글로 닉네임을 등록한 적 없는 사용자는, 첫 평가 시 4자 이상 비밀번호로 닉네임을 새로 등록하게 된다.
- 익명("익명")으로는 평가가 검증 없이 진행되지만, 평가 폼은 닉네임을 요구하므로 실무상 닉네임+비밀번호가 필요.
- 회귀 위험 낮음: 기존 `ensureNicknameOwnership` 헬퍼를 재사용하며 글·댓글과 동일 패턴.

## 한계 (변경 없음)
- 새 닉네임을 정식 생성(비밀번호 설정)해 다시 평가하는 것은 여전히 가능. 익명·무로그인 방침상 의도적으로 허용.
