# 문제ZIP 대량 참여(≈600명) 부하 최적화 (위험 검토 반영판)

점검 결과 인덱스·댓글수 집계는 양호. 아래 변경은 **서버 호출을 줄이는 방향**이라 서버비를 오히려 낮추고, 회귀 위험을 최소화하도록 설계함.

## 변경 1 — 좋아요 상태 배치 조회 (읽기 부하 최우선)
문제ZIP 카드가 카드마다 `getLikeState`를 호출해 600카드면 열람 1회에 600호출 발생. 이를 페이지당 1회로 축소.

- `LikeButton.tsx`에 **선택적 제어 props** 추가: `count?`, `liked?`. 
  - props가 주어지면 자체 `useQuery`를 끄고(`enabled:false`) 표시값으로 사용, 토글은 로컬 상태로 갱신.
  - props가 없으면 **기존 동작 그대로** → 글 상세·댓글 좋아요는 코드 무변경(회귀 0).
- `_main.board.$slug.index.tsx`: 현재 문제ZIP 페이지에 보이는 카드 id들을 모아 `getLikeState`를 1회 호출하는 `useQuery` 추가, 결과를 `ProblemCard` → `LikeButton`에 props로 전달.

## 변경 2 — 문제ZIP 목록 페이지네이션 (읽기 부하)
일반게시판과 동일하게 문제ZIP도 `PAGE_SIZE(10)`씩 페이지네이션.
- `validateSearch`에 `ppage` 추가(기본 1, 하위호환), 기존 `BoardPagination` 재사용.
- 결과적으로 변경 1의 배치 조회는 페이지당 최대 10개 id만 요청(→ `getLikeState`의 200개 상한 여유, 청크 불필요).
- 렌더링 카드 수도 600→10으로 감소.

## 변경 3 — 게시글 번호 채번 안정화 (쓰기 부하, 저위험안)
`createPost`는 5개 작성 흐름이 공유하고 정합성은 이미 유니크 제약이 보장하므로, **전면 재작성 대신 최소 침습**으로 강화:
- 재시도 횟수 3 → 8회로 상향하고, 재시도 사이 짧은 지수 백오프(예: 20·40·80ms…) 추가.
- 이것으로 현실적 동시성(수십 건)에서 실패를 사실상 제거.
- (선택·후속) 극단적 동시성이 실측되면 그때 `pg_advisory_xact_lock` 기반 원자 INSERT RPC로 승격. 이번엔 포함하지 않음(공유 로직 위험 회피).

## 검토 결론 (요청 사항 확인)
- **서버비 과다**: 없음. 좋아요 배치+페이지네이션으로 호출량 대폭 감소. 신규 폴링/실시간/크론 없음. 문제ZIP 제출은 OG 외부요청도 없음.
- **기능 오작동**: 낮음. LikeButton은 선택적 props로 하위호환, 페이지네이션은 문제ZIP 섹션 국한.
- **다른 기능 악영향**: 채번을 저위험안으로 조정해 5개 작성 흐름에 대한 위험 제거. 상세/댓글 좋아요·딥링크·닉네임 로직 무영향.
- **가이드(/guide)**: 기능 추가/삭제가 아니라 성능 개선이라 문구 변경 불필요(문제 목록이 페이지로 나뉘는 UI 변화만 있음).

## 검증
- 게시판 로드 시 네트워크 탭에서 `getLikeState` 호출이 페이지당 1회인지 확인.
- 5개 작성 폼(일반/질문/링크/산출물/문제ZIP) 모두 정상 등록 확인.
- `createPost` 병렬 호출 스크립트로 동시 제출 시 순번 중복/실패 없음 확인.
- 글 상세·댓글 좋아요 토글이 기존과 동일하게 동작하는지 확인.
